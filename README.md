# CBP Research Network — Evidence Engine (Proof of Concept)

A small, real, working demonstration of the platform's core AI research layer:
retrieval-augmented generation grounded in 9 real Chiropractic BioPhysics (CBP)
research papers, plus a real Bayesian meta-analytic pooling of the actual effect
sizes those papers report.

**What's genuinely real here** — no mocked data, no scripted chat:

- **Corpus**: all 9 papers were OCR'd in full (not just abstracts) and chunked into ~730 real, citable passages with page numbers.
- **Retrieval**: a from-scratch BM25 lexical search engine (`src/bm25.js`) scores every question against the real corpus. No vector DB, no external retrieval service — transparent and deterministic.
- **Generation**: retrieved passages are sent to a live OpenAI API call (`src/llm.js`, `gpt-4o-mini` by default), instructed to answer *only* from those passages and to cite each claim — and instructed to respond with an explicit `INSUFFICIENT_SOURCES:` marker instead of an answer if the retrieved passages don't support the question, or if the question tries to get it to ignore the source restriction. The server parses that marker into `grounded: false` and hides the source list for that response, since the model itself judged those passages irrelevant. If no `OPENAI_API_KEY` is configured, or the API is unreachable, the app is still honest and still useful — it shows the real retrieved sources with a clear message that synthesis wasn't available, rather than crashing or going silent.
- **Retrieval quality gate**: weak BM25 matches (score below `MIN_RETRIEVAL_SCORE`, default 10) are dropped before they ever reach the LLM or the UI, so a genuinely out-of-corpus question doesn't surface unrelated passages just because a word or two happened to overlap.
- **Bayesian synthesis**: `src/bayesian.js` performs real inverse-variance-weighted pooling of the actual reported effect sizes per spinal region (cervical, lumbar, thoracic), sourced from `data/bayesian-inputs.json`. Every input is traceable to a real number in a real paper; anywhere a standard deviation had to be estimated rather than read directly off the page, it's labeled `"estimated"` with the method documented inline.

**What's explicitly out of scope for this POC** (stated on the Overview tab too, so nobody mistakes it for the full product): only 9 of the network's 341+ papers are indexed, there's no live clinic registry yet, and the Clinic/Policy dashboard tabs are placeholders pointing at the real engines rather than full builds.

## Architecture

```
server.js              Express app: sessions, static files, all routes
src/auth.js             Role + shared-passcode login (4 roles, no user DB)
src/bm25.js              From-scratch BM25 retrieval over the chunked corpus
src/bayesian.js          Real inverse-variance-weighted Bayesian pooling
src/llm.js               Server-side, grounded OpenAI API call (key never reaches the browser)
data/papers-meta.json    The 9 papers' citations
data/chunks.json         ~730 real chunked passages (generated by scripts/build-chunks.js)
data/extraction-table.json   Structured, human-verified numbers pulled from each paper
data/bayesian-inputs.json    Real per-region effect-size inputs + methodology notes
corpus/*.txt             Full OCR'd/extracted text of all 9 papers
public/login.html        Role + passcode login page
public/dashboard.html    The dashboard — Evidence Library and Bayesian Synthesis tabs are live
```

Rebuilding the chunk index (only needed if you edit `corpus/*.txt` or `data/papers-meta.json`):

```bash
npm run build:chunks
```

## Run locally

```bash
npm install
cp .env.example .env
# edit .env — at minimum set OPENAI_API_KEY if you want live prose synthesis
npm start
```

Open `http://localhost:3000` — you'll land on the login page. Use any of the four
role passcodes from your `.env` (defaults are in `.env.example`).

## Deploy to Railway

**Option A — connect a GitHub repo (recommended):**

1. Push this folder to a new GitHub repository.
2. In Railway: **New Project → Deploy from GitHub repo** → select the repo.
3. Railway auto-detects Node via Nixpacks and runs `npm install` then `npm start` (see `railway.json`).
4. In the Railway project's **Variables** tab, set:
   - `OPENAI_API_KEY` — from https://platform.openai.com/api-keys
   - `OPENAI_MODEL` — optional, defaults to `gpt-4o-mini` if unset
   - `SESSION_SECRET` — any long random string (`openssl rand -hex 32`)
   - `PASSCODE_CLINIC`, `PASSCODE_RESEARCHER`, `PASSCODE_NETWORK_ADMIN`, `PASSCODE_EXECUTIVE` — your own values, don't ship the defaults
   - `MIN_RETRIEVAL_SCORE` — optional, defaults to `10`; raise it to be stricter about what counts as a relevant match
5. Railway assigns a public URL automatically — that's the link to send Beth.

**Option B — Railway CLI, from this machine:**

```bash
npm install -g @railway/cli
railway login
railway init
railway up
railway variables set OPENAI_API_KEY=sk-...
railway variables set SESSION_SECRET=$(openssl rand -hex 32)
railway variables set PASSCODE_CLINIC=... PASSCODE_RESEARCHER=... PASSCODE_NETWORK_ADMIN=... PASSCODE_EXECUTIVE=...
```

No database, no external services beyond the OpenAI API — this is a single
small Node process, so Railway's free/starter tier is more than sufficient for
a demo link.

## Roles

| Role | Passcode env var | Default landing tab |
|---|---|---|
| Clinic / Chiropractor | `PASSCODE_CLINIC` | Clinics |
| Researcher | `PASSCODE_RESEARCHER` | Evidence Library |
| Network Admin | `PASSCODE_NETWORK_ADMIN` | Overview |
| Executive & Policy | `PASSCODE_EXECUTIVE` | Policy |

All four roles can navigate to every tab after signing in — the role only
determines the default landing tab and the badge shown in the header. This is
a deliberate proof-of-concept choice: it's one shared passcode per role rather
than individual accounts, appropriate for a link one prospect is testing, not
a production multi-tenant system.

## Security note

The OpenAI API key lives only in Railway's environment variables and is
read server-side in `src/llm.js` — it is never sent to the browser or embedded
in any file. Do not commit a `.env` file with real secrets to git (`.gitignore`
already excludes it). A network failure or API outage on OpenAI's side is
caught and reported gracefully (`reason: "network_error"` / `"api_error"`) —
it will not take the whole server down for other users.

## Testing the grounding behavior

`Core evidence-Questions.docx` in this folder has 50 test questions grouped by
what they're checking — core evidence, cross-paper comparisons, exact numbers
to fact-check against the PDFs, Bayesian reasoning, and (most importantly)
6 adversarial questions (#45–50) designed to try to get the assistant to
hallucinate or ignore its sourcing restriction. Those should each come back
either declining to answer or answering narrowly from a real cited passage —
never with an invented fact, name, or statistic. That's the credibility proof
point worth running live in front of anyone evaluating this.
